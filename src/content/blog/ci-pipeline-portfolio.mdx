## The premise

I'm a QA Automation Engineer. My portfolio makes claims about test coverage, accessibility standards, and CI/CD expertise. If those claims weren't verifiable, the site would be undermining its own message.

So I made a rule: **every quality claim on the site must be backed by an automated gate running in CI.**

## What that looks like in practice

The site is a Next.js 16 static export with two languages, an interactive WebGL topology, and a full test suite. The CI pipeline runs three job types on every push:

```yaml
# .github/workflows/ci.yml (simplified)
jobs:
  build:
    steps:
      - Check formatting # prettier --check
      - Linting # eslint
      - Security audit # npm audit --audit-level=high
      - Type checking # tsc --noEmit
      - Run tests # jest --coverage
      - Build # next build
      - Bundle size check # size-limit

  e2e: # Playwright + axe-core
    needs: build
    steps:
      - E2E tests # ~65 tests across desktop and mobile viewports
      - WCAG scans # axe-core on the home, quality dashboard, and ES routes

  lhci: # Lighthouse CI
    needs: build
    gates:
      - a11y ≥ 90
      - best-practices ≥ 95
      - SEO ≥ 95
```

## The coverage gate

The Jest configuration enforces coverage close to full on branches, functions, lines, and statements:

```json
{
  "coverageThreshold": {
    "global": {
      "branches": 97,
      "functions": 99,
      "lines": 99,
      "statements": 99
    }
  }
}
```

This isn't about the exact number. It's a forcing function for testable architecture. When a component is hard to test, I redesign it — I don't lower the threshold. The suite runs several hundred Jest tests across dozens of suites, plus property-based testing (fast-check) on the domain logic.

## What a gate like this is for

A CI pipeline like this catches the class of problems that are easy to miss in a manual review: broken structured data, accessibility regressions, a bundle that quietly grew past budget, a route that 404s after a rename. None of that is exotic — the value is that it runs on every push instead of depending on someone remembering to check.

## The maintenance cost

The build, e2e, and Lighthouse jobs run in parallel; the slowest of the three is usually the e2e job, in the few-minutes range. The test maintenance is real — every new component needs tests, every route change needs updated E2E selectors — but the cost is predictable and front-loaded rather than showing up later as a production bug.

## Is it worth it?

For a personal portfolio? Yes — if your craft IS quality engineering. A recruiter who clicks the CI badge sees the pipeline actually run, not just a claim in a bullet point.

## How to start

If you want to do something similar:

1. Start with a single GitHub Actions workflow that runs `npm test` and `npm run build`
2. Add type checking (`tsc --noEmit`) — it catches more real bugs than linting
3. Add a coverage threshold at a level that makes sense for your project
4. Add a bundle size check — `size-limit` takes 5 minutes to configure
5. Layer on E2E testing once your routes are stable (Playwright + axe-core for a11y)

The key is to make the pipeline **actionable** — if it fails, you should know exactly what to fix. No flaky tests, no ignored thresholds.

## The problem with coverage gates

Most teams set a coverage threshold (80%, 90%) and call it done. The problem is that these numbers drift. A few merges here, a few "I'll add tests later" comments there, and suddenly your 90% coverage is 74% and nobody noticed until the next audit.

## The solution: hard gates in CI

The key insight is that coverage thresholds should be **enforced mechanically**, not tracked manually. Here's how I set it up:

### Step 1: Jest configuration

```json
{
  "jest": {
    "coverageThreshold": {
      "global": {
        "branches": 97,
        "functions": 99,
        "lines": 99,
        "statements": 99
      }
    }
  }
}
```

Branches sit a couple points below the rest — some UI branches (WebGL fallback paths, third-party error boundaries) aren't worth contorting a component to hit 100% on. The gate is set close to what's actually achievable, not at a round number for its own sake.

### Step 2: GitHub Actions workflow

```yaml
- name: Run tests with coverage
  run: npm test -- --coverage

- name: Check coverage threshold
  run: |
    if [ $? -ne 0 ]; then
      echo "Coverage below threshold — failing build"
      exit 1
    fi
```

### Step 3: Handle edge cases

Not every branch is easily testable. For genuine edge cases (error boundaries, third-party API failures), use `/* istanbul ignore next */` sparingly, and revisit those ignores periodically instead of letting them accumulate silently.

## Results

On this portfolio, coverage currently sits at 99%+ on statements, functions, and lines, with branches close behind. The value isn't the exact number — it's the forcing function for testable architecture: if something is hard to test, redesign it rather than lower the threshold.
